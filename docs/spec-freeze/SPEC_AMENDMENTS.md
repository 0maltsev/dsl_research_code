# Specification amendments and clarifications

The paper snapshot is immutable. This ledger records every implementation resolution that is not fully determined by it. “Propagate” means the change should be applied to the separate paper repository before a results-bearing manuscript or preregistration is frozen.

## AM-001 — Concrete source grammar and operator surface

- Source location: `main.pdf`, Appendix A.1 and Section 4.1; `EXPERIMENT_IMPLEMENTATION_SPEC.md` Section 2.1.
- Ambiguity: only abstract mathematical syntax is provided; declaration terminators, concrete bounded syntax, product syntax, typed bit tokens, and operator precedence are not mechanically parsable. Appendix A also says conveniences outside its lexical categories have no core meaning.
- Adopted resolution: `grammar.ebnf` defines a complete UTF-8 concrete syntax. Fixed infix/unary operators are one-for-one pre-core elaborations to primitive calls; postfix indexing is left associative; equality and comparison operators are non-associative. Elaboration occurs before semantic analysis and never optimizes or reorders.
- Scientific effect: no new primitive or event; source text becomes reproducibly parseable. Parser/elaboration conformance becomes part of PO-NORM evidence.
- Propagate to paper repository: **Yes**; add a concrete-syntax appendix or explicitly cite the artifact grammar.

## AM-002 — Product arity and projection numbering

- Source location: `main.pdf` Sections 4.1, A.1, and Table 7.
- Ambiguity: finite product arity has no lower bound, and concrete projection numbering is not fixed.
- Adopted resolution: product types and values have arity at least two; grouping parentheses are not products. `proj<j>(e)` uses one-based `j` in `[1,k]`, matching the paper's typing rule. Nullary functions remain permitted.
- Scientific effect: removes unit/unary-product corner cases without changing any planned kernel.
- Propagate to paper repository: **Yes**.

## AM-003 — Definition and scope of `Q_f`

- Source location: `main.pdf`, Table 6 rule C-Call versus Section 4.2 T-Call and Section 4.3 `K_f`; `Q_f` is otherwise undefined.
- Ambiguity: the count-call rule refers to `Q_f`, but the function environment stores only signature, result-size transformer `K_f`, and cost transformer `Phi_f`.
- Adopted resolution: a checked function environment entry is `Sigma(f)=(signature, K_f, Q_f?, Phi_f, rank)`. `Q_f` is present only when the declared result is `i32` and the body has an accepted count-refinement derivation. It is derived under exactly the same formal parameters, formal array-length symbols, constraints, and declaration rank as `K_f`; it names the returned word and stores `(lambda_f,u_f;nu_f)`. Call substitution for `Q_f`, `K_f`, and `Phi_f` is simultaneous, capture avoiding, and uses the same actual shape/footprint vector. If `Q_f` is absent, the call is legal as an ordinary expression but prohibited in the count fragment.
- Scientific effect: preserves intended compositional count calls without trusting arbitrary `i32` functions. Soundness relies on TH-CERT plus the existing declaration-rank and PO-SIZE-SUBST/PO-COST-CALL arguments; it adds no new theorem claim.
- Propagate to paper repository: **Yes, required before proof work**.

## AM-004 — Dynamic trace datatype and exact `peak_K`

- Source location: `main.pdf` Sections 5 and 6.1 and Appendix A.7.
- Ambiguity: the prose defines trace-aware composition and a maximum over semantic configurations but not a mathematical trace datatype, exact boundary samples, or a total composition operator.
- Adopted resolution: `cost-trace-semantics.md` defines traces as an initial snapshot followed by typed event/snapshot steps and a terminal outcome, compatibility-checked concatenation, active roots at every boundary, activation markers, and exact `peak_K` over all snapshots. Sequential constructs, selected branches, explicit calls, partial aggregate states, object death, and failures have explicit trace clauses.
- Scientific effect: eliminates peak ambiguity and prevents premise-peak undercount. It strengthens the object to which PO-COST-SOUND applies but does not claim the static equations are sound.
- Propagate to paper repository: **Yes, required before proving PO-COST-ERR/CALL/SOUND**.

## AM-005 — Total retained-footprint environment `Lambda`

- Source location: `main.pdf` Sections 6.2–6.3 and Appendix A.7.
- Ambiguity: `Lambda` is described as mapping aggregate variables to footprint expressions, but scalar entries, ABI parameters, local products/arrays, aliases, call formals, and results are not a total definition.
- Adopted resolution: `cost-trace-semantics.md` defines `Lambda` on every typed variable. Scalars map to zero. Export ABI aggregates map to zero local bytes. Earlier-function aggregate formals receive footprint variables instantiated from actual result-footprint bounds. Let/fold/body binders receive the bound expression/accumulator transformer. Products sum component candidates, arrays include their capacity region plus upper-bounded logical element graphs, and duplicate references are conservatively counted. Every expression form has total `L` and `P` equations or is rejected when its retained-root transformer is unavailable.
- Scientific effect: makes analyzer behavior deterministic and conservatively alias safe; exactness may decrease through overcount. The call/alias soundness obligations remain open.
- Propagate to paper repository: **Yes**.

## AM-006 — Complete scalar and aggregate ABI

- Source location: `main.pdf` Sections 7.5, A.7, and A.8; the paper fixes only broad header, width, alignment, and export shape.
- Ambiguity: Boolean encoding, `A(tau)`, product offsets/padding, nested aggregates, root records, output ownership, exact export names, aliasing, padding, and host/module validation are incomplete.
- Adopted resolution: `abi-layout.md` freezes widths/alignments, canonical product flattening, array objects and capacity trees, absolute little-endian offsets, input/output record headers, padding, nested arrays/products, disjointness, caller-owned deep-copy results, export names/signature, status, trap policy, and host obligations.
- Scientific effect: fixes ABI work included in RQ3/RQ5 and makes layout/address evidence reproducible. It can affect measured overhead and must be identical across execution forms.
- Propagate to paper repository: **Yes, required before performance preregistration**.

## AM-007 — Boolean and padding validity

- Source location: `main.pdf` Sections 3.2, 7.5, and A.8.
- Ambiguity: the width of Boolean is given indirectly, but valid ABI words and padding contents are not fixed.
- Adopted resolution: Boolean is a 32-bit little-endian word and only `0` and `1` are valid. Every input reserved field, alignment byte, unused root byte, unused array-capacity byte, and ignored preallocated nested object byte is zero. The output region is zeroed before invocation and all output padding remains zero.
- Scientific effect: removes multiple encodings and uninitialized-byte/hash leakage; adds symmetric ABI validation/zeroing work.
- Propagate to paper repository: **Yes**.

## AM-008 — Floating output and NaN observation

- Source location: `main.pdf` Sections 3.2, 7.6, and 8.1.
- Ambiguity: source primitives canonicalize NaNs while scalar Wasm observations quotient them; it is not explicit whether output serialization itself canonicalizes.
- Adopted resolution: the reference evaluator and C++ oracle canonicalize after every floating primitive. Scalar Wasm may serialize any Wasm-permitted NaN word. Output serialization does not add a canonicalization step; correctness applies the NaN quotient. Non-NaNs, including signed zero, are exact bits.
- Scientific effect: preserves the paper's target observation relation and avoids inserting unmodelled target work. Raw output hashes involving NaNs must also record the normalized observation hash.
- Propagate to paper repository: **Recommended clarification**.

## AM-009 — Canonical BIR capability vocabulary

- Source location: `main.pdf` Section 7.2 uses long names while Appendix B.1 uses `inR`, `fresh`, `imm`, `scratch`, `outW`; `EXPERIMENT_IMPLEMENTATION_SPEC.md` Section 3.2 names four kinds.
- Ambiguity: vocabulary and whether sealed immutable storage is a fifth capability kind conflict.
- Adopted resolution: the only kinds are `inputRead`, `freshInit`, `scratchInit`, and `outputWrite`. Builder prefix/sealed state and initialized coverage are state fields. `seal` changes `freshInit` from building to sealed-read state without creating an `imm` kind. `reserve` consumes a suitable scratch/output subrange and creates `freshInit`.
- Scientific effect: no semantic change intended; the complete transition system is now testable and serialized records use one vocabulary.
- Propagate to paper repository: **Yes**.

## AM-013 — Fixed Wasm exports and source status mapping

## AM-014 — Static array region versus nested aggregate capacity tree

- Source location: `main.pdf` Appendix A.7 defines `region(tau,N)` but does not define a complete nested ABI graph layout.
- Ambiguity: arrays containing arrays/products require offsets and bounded descendant storage; `region` alone covers only the immediate object.
- Adopted resolution: `region(tau,N)` remains the immediate source-object charge used by the source cost model. `TreeBytes(tau)` in `abi-layout.md` is a separate target ABI capacity-tree extent that recursively reserves descendant array objects in deterministic preorder. Source `h`/`p`, ABI input/output bytes, BIR frames, and total linear memory remain separate metrics.
- Scientific effect: prevents target ABI capacity from being mislabeled as source scratch or cumulative reservation.
- Propagate to paper repository: **Yes, as an ABI clarification**.

## AM-015 — BIR primitive error edge and call return shape

## AM-017 — Lexer-level decimal-numeral range and unsupported-construct detection shapes

- Source location: `grammar.ebnf` lexical constraint 7 and the `decimal`/`positive-decimal`/`capacity` productions; `SPEC_FREEZE.md` "Frozen language boundary"; `diagnostics-and-status.md` `LEX006`/`LEX007`.
- Ambiguity, part (a) — numeral range bound: `SPEC_FREEZE.md`'s "Frozen language boundary" states the `[0, 2^31-1]` bound only for *capacities* ("Capacities are decimal natural literals in `[0, 2^31-1]`"), and `grammar.ebnf` lexical constraint 7 ties its leading-zero/overflow rule to "Capacity evaluation" by name. But `grammar.ebnf` also defines `positive-decimal` (used only for the projection index `proj<j>(e)`) as a distinct nonterminal that lexically reduces to the exact same digit-run shape as `capacity`/`decimal`, and a standalone tokenizer cannot tell from the digits alone which of the two a given numeral will turn out to be used as — that distinction is made only once a parser places the token inside a `projection-expression` versus an `array-type`/`fold-expression`/`build-expression`/`array-literal`. The grammar and `SPEC_FREEZE.md` do not say whether an over-`2^31-1` or leading-zero projection-index numeral is a lexical error (`LEX006`) or must be accepted lexically and rejected later once its syntactic role is known (plausibly under `TYP007`, "Projection index is outside one-based product arity," or a new code).
- Ambiguity, part (b) — `LEX007` trigger shapes: `diagnostics-and-status.md` defines `LEX007` only as "Source comment or decimal floating literal is unsupported in language 0.1.0"; no document specifies what comment syntax or floating-literal shape should be *recognized* in order to raise this code instead of a generic `LEX002`/`LEX003`.
- Implemented in `src/source/lex` (Phase 2.1, 2026-10-05), pending this entry's approval:
  - (a) The lexer applies the same `[0, 2^31-1]` bound to every bare decimal numeral it tokenizes, regardless of eventual syntactic role, and reports `LEX006` for any violation. This is the narrowest resolution available to a context-free tokenizer (there is no other stated bound anywhere a decimal numeral appears), but it is an extension beyond what `SPEC_FREEZE.md`'s sentence literally names.
  - (b) The lexer treats `//` and `/*` (the standard C-family forms, matching this language's overall syntax) as comment attempts, and a digit-run immediately adjacent to `.` (either `digits.` or `.digits`, with or without digits on the far side) as a floating-literal attempt, both raising `LEX007`; nothing else does.
- Scientific effect: both are implementation-only lexical-diagnostics-and-recovery details. Neither changes which *programs* are ultimately accepted or rejected, what core node any accepted program elaborates to, any cost/trace event, or any ABI/BIR/Wasm behavior — they only change which specific diagnostic code (and, for (a), lexer-versus-parser stage) a specific class of rejected input receives. No kernel (K1/K2/K3) or dataset depends on either choice.
- Propagate to paper repository: **No** (concrete-syntax-conformance detail below the level the paper specifies; same category as `AM-001`'s grammar but narrower).
- Status: **APPROVED (2026-10-05)**, both parts as shipped. A `spec-auditor` review of the Phase 2.1 milestone found this behavior had been implemented and locked into shipped tests without first being logged here or put to the author, per `CLAUDE.md` §5's stop-and-ask protocol; this entry and the accompanying `AskUserQuestion` are the correction. Author approval given in a Claude Code session on 2026-10-05, in reply to the recommendation for each part above: (a) "Lexer applies the bound to every numeral" — the lexer continues to apply `[0, 2^31-1]` to every bare decimal numeral regardless of eventual syntactic role; (b) "Yes, keep `//` and `/*` plus digit-adjacent-dot" — the `LEX007` trigger shapes are unchanged. No code or test changes were required by this approval.

- Source location: `grammar.ebnf` "Static concrete-syntax constraints" item 6 ("An array literal with `m` elements requires `m <= N`"); `diagnostics-and-status.md` `SIZ002` ("Array literal length exceeds capacity"), catalogued under "Size/count diagnostics," a separate table from `LEX`/`SYN`; `docs/architecture.md`'s module-ownership table, which names `src/source/size` (not `src/source/parse`) as owning "Shapes, count refinements, finite certificate checking" and states `src/source/parse`'s row "Must not own: Name, type, size, or cost decisions" with no stated exception.
- Ambiguity: `grammar.ebnf`'s own "static concrete-syntax constraints" list mixes items that are clearly parser-level (item 2, product/array arity at least two, which `src/source/parse` already enforces as `SYN003`) with at least one item that is clearly *not* parser-level by the grammar's own design (item 4, duplicate declaration/parameter names, which is explicitly a name-resolution concern for `src/source/resolve`, Phase 3). The only difference is which module/phase performs the check and therefore which stage's traceability/test suite is responsible for it, and whether an untyped AST may transiently carry an over-length array literal between Phase 2 and Phase 3.

## AM-019 — Which code a direct self-recursive call raises, and which module raises it

- Source location: `main.pdf` §4.1 (p.10: "The body of `g` may call only `f` with `f ≺_M g`; hence the call graph is acyclic. There is no ... recursion...") and §4.4 (p.12, one rejection bullet: "mutation, address observation, import, host access, general allocation, recursion, or a call not satisfying `f ≺_M g`"); `diagnostics-and-status.md` `NAM006` ("Call target is not strictly earlier than caller") and `EFF004` ("Recursion or cyclic call graph"), the latter catalogued under "Effect/termination diagnostics"; `docs/architecture.md`'s module table, which assigns `src/source/resolve` only "Symbols, alpha-renaming, declaration ranks" and assigns "Exhaustive typing and effect rejection" to `src/source/typecheck` (Phase 3.2, not yet implemented).
- Ambiguity: the paper's one formal premise for every call is `f ≺_M g` (a single strict total order by declaration rank); self-recursion (`f` calling `f`) is simply the case `f = g`, which already falls inside `NAM006`'s plain-English scope ("not strictly earlier" includes "equal"). Nothing in the paper or `diagnostics-and-status.md` states that self-recursion specifically must be distinguished from any other order violation by diagnostic code, and `EFF004`'s placement under "Effect/termination" (the category `docs/architecture.md` ties to `typecheck`'s "effect rejection," not `resolve`'s "declaration ranks") is at least as strong a textual signal that `EFF004` belongs to a *different* module than the equally plausible reading that `resolve` is best-placed to give self-calls a clearer, dedicated diagnostic. Unlike `AM-017`/`AM-018`, the two readings are not merely "same programs, different code": `resolve` necessarily runs before `typecheck` and already rejects every `f ≺_M g` violation (self-calls included) via its own check, so if `resolve` does *not* special-case self-calls, `typecheck` would never receive an order-violating module to apply `EFF004` to at all -- making `EFF004` structurally unreachable in the implemented pipeline (the same kind of honestly-disclosed dead-code situation already accepted for `SYN003`), not merely differently-labeled.
- Implemented in `src/source/resolve` (Phase 3.1, 2026-10-05), pending this entry's approval: a call whose target has the *same* declaration rank as the caller (i.e. is the caller itself) raises `EFF004`; any other call whose target does not have a strictly smaller rank raises `NAM006`.
- Scientific effect: none on which programs are ultimately accepted — both readings reject exactly the same set of programs (every `f ⊀_M g` call, self-calls included). The difference is which diagnostic code a self-recursive call receives, which module's test suite is responsible for exercising it, and whether `EFF004` is ever reachable at all given `resolve` runs first.
- Propagate to paper repository: **No** (diagnostic-code/module-boundary detail below the level the paper specifies).
- Status: **APPROVED (2026-10-05)**, as shipped. A `spec-auditor` review of the Phase 3.1 milestone found this split had been implemented and asserted in `STATUS.md`/`docs/traceability.md` without first being logged here or put to the author — the same failure class `AM-017` and `AM-018` already corrected twice this phase. Author approval given in a Claude Code session on 2026-10-05, choosing "Resolve raises EFF004 for self-calls (Recommended)": `src/source/resolve` continues to raise `EFF004` for a direct self-call and `NAM006` for any other call-ordering violation. No code change was required by this approval.

## AM-020 — What type an empty array literal typechecks to

- Source location: `grammar.ebnf` line 67-68 (`array-literal = "array", "<", capacity, ">", "[", [ expression, { ",", expression } ], "]"` — the element list is syntactically optional, zero elements included) and the already-committed Phase 2.2 test `tests/source/parse/test_parse_arrays_products_proj_index_len.cpp`'s `empty_array_literal_is_valid()`, which asserts `array<4>[]` parses successfully; `main.pdf` Table 7 (`app:typing-size`), rule T-Array: "`m ≤ N` and every `e_i : τ`" concludes "literal: `arr⟨τ, N⟩`"; `main.pdf` §4.2's only stated typing judgment is the single unidirectional synthesis form `Σ; ∆; Γ ⊢ e : τ` (no bidirectional/checking-mode judgment against an expected type is stated anywhere in the paper).
- Ambiguity: T-Array synthesizes the literal's element type `τ` from its own elements ("every `e_i : τ`"). When `m = 0` there are no elements to synthesize `τ` from, and the paper states no fallback (no bidirectional propagation from an enclosing expected type, such as the declaring function's result type, is stated anywhere in Table 7 or §4.2's prose — every other T-rule is likewise pure synthesis with no "check against expected type" premise). The grammar nonetheless makes `array<N>[]` syntactically legal and the parser already accepts it (Phase 2.2, committed), so this case is reachable and typecheck must decide something for it.
- Recommendation: reject an empty array literal in `src/source/typecheck` (no `τ` can be synthesized, so T-Array yields no derivation when `m = 0`; per `main.pdf` App. A.5's "A missing derivation rejects the module"), reusing `TYP008` ("Array literal elements are heterogeneous") for this case rather than minting a new diagnostic code — an empty element set has no single shared type any more than a conflicting one does, and this avoids amending the frozen `diagnostics-and-status.md` catalogue for one narrow edge case. Alternatives considered: (b) mint a new code (e.g. `TYP013`) specifically for "cannot synthesize the type of an empty array literal"; (c) make T-Array bidirectional only for this case, inferring `τ` from an enclosing expected type (e.g. the declaring function's result type) where one is syntactically available. Scientific effect: none of the three changes which *other* programs are accepted; they differ only in whether `array<N>[]` is ever well-typed and, if rejected, which code names the rejection.
- Propagate to paper repository: **No** (implementation-level typing-rule edge case below the level the paper specifies; the paper's silence here is about an edge case in its own synthesis judgment, not a contradiction).
- Status: **APPROVED (2026-10-05)**, option (a). Author approval given in a Claude Code session on 2026-10-05, choosing "Reject via TYP008 (Recommended)": `src/source/typecheck` raises `TYP008` for an empty array literal (`m = 0`), on the reading that an empty element set has no determinable shared type any more than a conflicting one does; no new diagnostic code is added.

## AM-021 — Which diagnostic a function body's type mismatch against its declared result type raises

- Source location: `main.pdf` Table 7 (`app:typing-size`) is titled "Typing rules for every **source expression** form" and every listed rule (T-Var through T-Call) types an *expression*; a function declaration `f(x1:τ1,...,xk:τk):τr = e` is a module-level construct, not itself one of the listed expression forms, so Table 7 states no named rule for checking the body `e`'s synthesized type against the declared result annotation `τr`. `main.pdf` App. A.5's module-check paragraph ("A module check traverses declarations in order and stores only derivations of type... A missing derivation rejects the module") confirms this check must happen somewhere, without naming which rule or code covers it. `diagnostics-and-status.md`'s `TYP001`-`TYP012` catalogue has no entry literally worded "function body/declared result type mismatch"; the closest candidates are `TYP002` ("Function actual arity or type mismatch") and `TYP003` ("Let/binder annotation or resolved use type mismatch").
- Ambiguity: `TYP002`'s wording ("actual arity or type") most naturally reads as the T-Call premise "ordered actual types agree" — a call site's arguments vs. the callee's declared parameters — not a declaration's own body vs. its own result type. `TYP003`'s "Let/binder annotation" is the better textual fit on the theory that a function declaration's result-type annotation is itself a kind of "binder annotation" (the function's only annotated, non-call-site, non-parameter construct besides parameters themselves) being checked against its "resolved use" (the body's synthesized type) — but this requires reading "binder" broadly enough to include a function declaration, which the catalogue does not state explicitly, and plain `let` bindings have no syntactic type annotation at all (`grammar.ebnf`'s `let-expression` carries none) to literally mismatch against, so `TYP003`'s literal text does not unambiguously name this case either.

## AM-023 — What exactly `C-Add`/`C-Sub`'s "certificate `NW_+`"/"`NW_-`" obligation requires a proof of

- Source location: `main.pdf` Appendix A.4 (p.37): "Write `NW_+(ν1,ν2,ν)` for `ν=ν1+ν2 ∧ 0≤ν≤2^31−1`, and `NW_−` for `ν=ν1−ν2 ∧ 0≤ν2≤ν1≤2^31−1`." Table 6 (p.38): `C-Add` | Premises: "operands `(λ_i,u_i;ν_i)`; certificate `NW_+`" | Result: "`(λ1+λ2,u1+u2;ν)` if both exact, else `(⋆,u1+u2;ν)`". `C-Sub` | Premises: "operands `(λ_i,u_i;ν_i)`; certificate `NW_-`" | Result: "`(λ1−λ2,u1;ν)` if both exact, else `(⋆,u1;ν)`".
- Ambiguity: `NW_+`/`NW_-` are defined as three-argument schematic predicates (parameterized over `ν1,ν2,ν`, the judgment's semantic/dynamic-value components), but the table does not spell out which *concrete* terms the "certificate `NW_+`"/"`NW_-`" premise instantiates them with at a `C-Add`/`C-Sub` application, nor how many separate facts must be certified (one, covering only the upper-bound combination that is present in both the exact and inexact result branches; or two, separately certifying the exact-value combination whenever that branch applies). `src/source/size/count`'s `CountResult` (Phase 3.4's first slice, already implemented and `spec-auditor`-reviewed) deliberately does not track `ν` as an explicit term at all (grounded in: none of the 3 already-implemented rules' own premises need it as an input) — if `NW_+`/`NW_-`'s obligation genuinely required certifying a fact *about* `ν1`/`ν2`/`ν` specifically (as opposed to `u1`/`u2`/`u` or `λ1`/`λ2`/`λ`, which the implementation does track as terms), that design would need revisiting for this rule specifically.
- Recommendation: read the obligation as exactly one certified fact per application, over the *upper bounds* specifically (not `ν`, and not a second independent fact for the exact case): `C-Add` certifies `0 ≤cert (u1+u2) ∧ (u1+u2) ≤cert 2^31-1` (the `0≤` half is free/structural, since upper-bound terms are built only from naturals by the term grammar `t::=n|ξ|t+t|kt`, so the real content is `u1+u2 ≤cert 2^31-1`); `C-Sub` certifies `u2 ≤cert u1` (preventing the subtraction from going negative; no upper-range fact needed beyond what `u1` already carries from however it was itself established). No *separate* certificate is needed for the exact-value case (`λ1+λ2`/`λ1−λ2`) in either rule: given the invariant that an already-established `(λ,u)` pair always satisfies `λ≤u` (maintained by construction at every point `src/source/size/count` produces a `CountResult`, not re-verified per step), `λ1+λ2 ≤ u1+u2 ≤cert 2^31-1` follows by the certificate module's own `ADD`+`TRANS` rules without a second obligation, and similarly for `C-Sub`. This reading lets `CountResult` continue to omit `ν` for `C-Add`/`C-Sub` specifically (consistent with the existing design), since the one real obligation is phrased entirely over `u`-terms.
- Scientific effect: a stricter reading (separately certifying the exact-value case too) would reject strictly fewer programs than this recommendation in no case (since the exact case's bound already follows from the upper-bound one plus the `λ≤u` invariant) — so the two readings are extensionally equivalent in what they accept, differing only in whether the implementation re-derives an already-implied fact. A reading requiring a direct fact *about* `ν` (not `u` or `λ`) would be a materially different, not yet designed-for, obligation shape.
- Propagate to paper repository: **No** (implementation-level certificate-obligation-instantiation detail below what the table's own shorthand notation spells out).
- Status: **APPROVED (2026-10-05)**, option (a). Author approval given in a Claude Code session on 2026-10-05, choosing "One obligation, over upper bounds only (Recommended)": `C-Add` certifies `u1+u2 <= 2^31-1`; `C-Sub` certifies `u2 <= u1`; no separate certificate for the exact-value case in either rule. `CountResult` continues to omit `ν`.

## AM-024 — How `C-Sub` represents an "exact" result given the size-term grammar has no subtraction constructor

- Source location: `main.pdf` Sec. 4.2 (p.9): size terms `t ::= n | ξ | t+t | kt` (no subtraction production). Sec. 4.2 (p.10): "Its exact component `λn` is either a term `sn`, with a checked derivation of `νn = sn`, or `⋆`" — i.e. a non-`⋆` exact component must literally be a term from this grammar. Table 6 (p.38), `C-Sub`: Result "`(λ1−λ2,u1;ν)` if both exact, else `(⋆,u1;ν)`" — written as if `λ1−λ2` were an ordinary term, the same way `C-Add`'s `λ1+λ2` is (and `λ1+λ2` *is* a valid term, via the grammar's `t+t` production).
- Ambiguity: `C-Add`'s exact-case result is always representable, because `t+t` is a grammar production. `C-Sub`'s is not: there is no `t-t` production, so "`λ1−λ2`" cannot literally be built as a `certificate::Term` the way `λ1+λ2` can, whenever `λ1`/`λ2` involve a free symbol (`ξ`). The table's notation does not distinguish this case from `C-Add`'s, leaving open whether (a) `C-Sub`'s exact case is only ever reachable when `λ1`/`λ2` are both *closed* (symbol-free), letting the implementation compute a concrete new `Literal` value directly (reusing the certificate module's own `evaluate_closed`-style reduction) and otherwise falling back to `⋆` even if both operands are individually non-`⋆`; or (b) the grammar is implicitly understood to extend with a subtraction production for this purpose that the table just doesn't restate; or (c) some other representation (e.g. `Scale(-1, ...)`-style negation) is intended, which the term grammar (restricted to `k ∈ N`, i.e. nonnegative scaling only) does not support either.
- Recommendation: option (a). `C-Sub`'s exact case is reachable only when both `λ1` and `λ2` are closed terms (no `Symbol` anywhere): compute their natural-number difference directly (certifying `λ2 ≤cert λ1` first, so the subtraction is itself nonnegative — the same closed/certified check `AM-023`'s `C-Sub` reading already requires, just applied to the exact terms instead of the upper bounds, when both happen to be closed and this certified fact is independently available), and represent the result as a fresh `Literal` term. Whenever either `λ1`/`λ2` is `⋆` or involves a free symbol, `C-Sub` falls back to `(⋆,u1;ν)` even though this differs from `C-Add`, where two non-`⋆` symbolic terms always combine into a new exact term via `t+t`. This is the minimal reading needing no grammar extension beyond what Sec. 4.2 states, and it reuses machinery (`evaluate_closed`-style closed reduction) this project has already built and `spec-auditor`-reviewed for Phase 3.3's `ClosedEval`.
- Scientific effect: a materially real asymmetry between `C-Add` and `C-Sub`'s exactness-preservation rate (fewer programs keep an exact count through a subtraction than through an addition) — but this follows directly from the term grammar's own asymmetry (an explicit `+` production, no `-` production), not from an invented restriction; the alternative readings (b)/(c) would require inventing grammar `main.pdf` does not state, which this entry's recommendation avoids.
- Propagate to paper repository: **No** (implementation-level term-representability detail; the paper's own term grammar is not itself contradictory, just silent on this specific instantiation).
- Status: **APPROVED (2026-10-05)**, option (a). Author approval given in a Claude Code session on 2026-10-05, choosing "Exact only when both operands are closed (Recommended)": `C-Sub`'s exact case is reachable only when both operands are closed terms, reducing via `evaluate_closed`-style natural-number subtraction (after certifying `λ2<=λ1`) to a fresh `Literal`; otherwise `⋆`, even when both operands are individually non-`⋆` symbolic terms. No grammar extension.

## AM-025 — Correcting `AM-023`: `C-Sub`'s "certificate `NW_-`" is unsound when certified over upper bounds alone (reopens `AM-023`'s `C-Sub` portion; `C-Add`'s portion is unaffected)

- Source location: `main.pdf` Appendix A.4 (p.37): `NW_-(ν1,ν2,ν)` is `ν=ν1−ν2 ∧ 0≤ν2≤ν1≤2^31−1` — a claim about the judgment's real `ν1`/`ν2` components, not about `u1`/`u2`. `main.pdf` Sec. 4.2 (p.10): "Its exact component `λn` is either a term `sn`, with a checked derivation of `νn = sn`, or `⋆`" — i.e. `λ` equals `ν` exactly whenever `λ` is present; `u` is only ever an *upper* bound on `ν`, never a lower one.
- Defect found: `AM-023`'s approved `C-Sub` reading (`u2 ≤cert u1`) is unsound. A `spec-auditor` review of this slice independently constructed and this session independently reproduced a concrete counterexample: `(i32bits(10) - i32bits(9)) - i32bits(2)`, i.e. `(10-9)-2`. The inner subtraction soundly produces `(λ=1, u=10)` (Table 6 keeps `C-Sub`'s upper bound at `u1` even though the real value is tighter -- this looseness is paper-specified, not itself a bug). The outer subtraction's real operands are `ν1=1, ν2=2`; `NW_-` requires `ν2≤ν1`, i.e. `2≤1`, which is **false** -- this expression deterministically underflows (`-1` in two's-complement). `AM-023`'s certificate check instead compares `u2≤u1` (`2≤10`), which holds, so the (buggy) implementation returned `ok=true` with an inexact result instead of rejecting via `SIZ006` -- independently reproduced in this session against the built libraries (`infer_count` on the body: `ok=1`, `exact present=0`). Root cause: certifying `u2≤u1` is a sound proxy for `C-Add`'s `NW_+` (addition is monotonic increasing in both operands, so upper-bounding both operands upper-bounds the sum), but is **not** a sound proxy for `C-Sub`'s `NW_-`: subtraction's no-underflow condition needs a *lower* bound on the minuend (`ν1`), which `u1` does not provide once `λ1` is absent or looser than `u1`.
- Recommendation: certify `u2 ≤cert λ1` instead of `u2 ≤cert u1`, and require `λ1` (the minuend's exact component) to be *present* for `C-Sub` to apply at all -- if `λ1` is absent (the minuend itself is inexact), reject via `SIZ006` rather than falling back to an inexact result, since there is then no sound lower bound on `ν1` available from `(λ,u)` tracking alone to compare `ν2` against. This is sound because `λ1`, when present, equals `ν1` exactly (per Sec. 4.2's own definition quoted above), so `ν2 ≤ u2 ≤cert λ1 = ν1` chains soundly. It is strictly more conservative than `AM-023`'s original reading (rejects a strict superset of programs: every case the buggy check wrongly accepted, plus nothing it previously rejected is newly accepted), and requires no change to `C-Add`'s already-sound `AM-023` portion or to `CountResult`'s shape (still no `ν`-bearing field; `λ1` already is the needed stand-in for `ν1` whenever it exists). An alternative, more general fix -- tracking an explicit lower-bound component in `CountResult` for every rule (not just `C-Sub`), letting `C-Sub` use a real lower bound on `ν1` even when `λ1` is absent -- would accept strictly more programs but requires revisiting every already-implemented rule's result shape, a materially larger redesign not undertaken here.
- Scientific effect: closes a real soundness gap (a deterministically-underflowing, well-typed program was silently accepted as a valid count derivation, violating the judgment's own `0≤ν≤u≤2^31-1` invariant, `main.pdf` p.10). The fix is conservative: it can only reject programs the buggy check wrongly accepted, never reject a program the (correct) `AM-023`/`AM-024` design intended to accept.
- Propagate to paper repository: **No** (implementation-level certificate-obligation-instantiation detail, not a paper contradiction; the paper's own `NW_-` definition was always correct, only this project's first instantiation of it was unsound).
- Status: **APPROVED (2026-10-05)**, option (a). Author approval given in a Claude Code session on 2026-10-05, choosing "Require minuend exact; certify u2<=lambda1 (Recommended)": `C-Sub` now requires `λ1` present, certifies `u2 <=cert λ1`, and raises `SIZ006` when `λ1` is absent or the certificate fails.

- Re-derived reasoning on (1)/(2): App. A.5's "does not allocate or evaluate `e`" framing means the shape derivation of the fold body cannot observe `i`'s *concrete runtime value* at any iteration — only its symbolic count-refinement identity (a fixed `IndexContext` entry, the same object Table 6's `C-Idx` and this module's `shape_of_var` already use), which is structurally identical regardless of which conceptual iteration is being considered. This is the exact argument `AM-031` already made for builder's `κb(i)`, and a `spec-auditor` review of that slice independently re-derived and confirmed it from the primary text, including checking that nested `if`/call/builder/fold constructs inside a body cannot smuggle in genuine per-iteration variation either. The only textual difference for "fold" is that `Kb` additionally takes the accumulator binder `x:τx` (per T-Fold's premise `Σ;∆n,0≤i<νn;Γ,i:idx(N),x:τx⊢eb:τx`, vs. T-Build's `Γ,i:idx(N)⊢eb:τ` with no `x`) — so `Kb(i,κi)`'s `i`-argument plausibly exists only because the body is typed/shaped *under* both binders textually, not because the transformer's *output* shape can depend on `i`'s value; `Kb` is accordingly read as `F(κ)`, a single pure function of the accumulator's own shape alone. Under that reading, `F(κ0)=κ0` (checked by *one* application) is a genuine fixed point: by ordinary induction, `F` applied again to `κ0` still yields `κ0`, so `κj=κ0` for *every* iteration index `j≥0` — sound for any exact `s` (even a non-literal symbol) and any upper bound `u` (even non-literal), with no unrolling, no literal-count requirement, and no new "symbolic iteration" machinery at all.
- Recommendation: option (a) **[recommended]** — scope this slice to exactly the sub-case the fixed-point argument above soundly covers. `shape_of_fold` takes the already-computed initial accumulator shape `κ0` and the already-computed "one-step" body shape `κ1` (the fold body's shape when the accumulator binder is bound to `κ0` — matching this module's established "already-computed, not `ast::Expr`" pattern every prior row function already follows; no callback/transformer abstraction is introduced). A new small structural-equality helper (`scalar`≡`scalar`; `array`≡`array` iff capacity equal and `exact`/`upper`/`element` each equal, reusing `certificate::terms_equal` and recursing into `element`; `prod`≡`prod` iff matching arity and each component equal) decides whether `κ0` and `κ1` coincide. If they do, the result is `κ0` itself (returned by pointer identity, mirroring `shape_of_builder`'s own test discipline) — sound for any count, exact or inexact, literal or symbolic, per the induction argument above. If they do not, raise `SIZ008` — a genuinely shape-varying accumulator (e.g. a fold that reconstructs a logically-growing array accumulator each iteration) is conservatively rejected rather than guessed at, spending `SIZ008` exactly where `AM-028` anticipated it, and matching `main.pdf` p.10's own general fallback principle ("a true formula for which no accepted certificate is supplied is conservatively rejected") generalized here to shape derivation. This is sound but incomplete — disclosed, not hidden: a fold whose accumulator shape genuinely stabilizes only after *more than one* step, or one a bounded literal-count unrolling could otherwise accept, is still rejected by this slice; both are left to a future, separately-scoped slice if broader coverage is wanted, exactly as `AM-026` narrowly scoped `C-Idx` alone before later building `check_count_admissibility`, and as `AM-031` scoped builder to its own degenerate case without building general join machinery nobody needed yet.
- Alternative options considered: (b) defer "fold" in its entirety to its own, later, more heavily-researched milestone (the same treatment already given to "call," which is blocked on `K_f`/`Q_f`/`AM-003`/`AM-022`'s still-deferred certificate-substitution mechanism) — leaves Phase 3.5's row buildout at 7 of 9 non-`call` rows (plus trivial "let") for this milestone cycle, with no new code or test coverage for "fold" at all; the narrower sub-case under option (a) is implementable today with no new unbuilt machinery, so deferring the whole row outright would forgo real, soundly-scoped progress for no corresponding risk reduction. (c) build a fuller version now that also handles a genuinely-varying accumulator via bounded literal-count unrolling (a caller-supplied per-step callback, invoked up to a concrete literal `s`/`u` when available) — not recommended for this slice: it needs a materially different interface (a transformer/callback, departing from every prior row's plain-already-computed-value pattern) and a separately-justified unrolling-bound policy, disproportionate to one milestone slice, and does not even help the merely-exact-but-symbolic or symbolic-upper-bound cases, which option (a)'s fixed-point check *does* already soundly cover.
- Scientific effect: a correct implementation of option (a) rejects a strict superset of what a complete fold-shape judgment would reject (conservative, not unsound) — it never wrongly accepts a shape bound that could actually be exceeded, since every accepted case is a genuine, soundly-derived fixed point. If the `Kb`-is-index-independent reading in sub-question (1) is ever found wrong for some language construct not yet considered, that would be a soundness-relevant finding requiring its own stop, exactly as `AM-023`'s analogous "approved but still wrong" `C-Sub` reading was later caught and corrected via `AM-025` — this entry's reasoning should accordingly be treated as requiring independent `spec-auditor` re-derivation after implementation, not as settled merely by this approval, consistent with this phase's own established lesson that being asked-and-approved is necessary but not sufficient.
- Propagate to paper repository: **No** (implementation-scoping decision for a first slice, not a paper contradiction; the underlying recurrence's operational realization for a non-literal exact/upper count remains genuinely underspecified in both Table 8 and the parallel footprint-descriptor treatment, which may be worth flagging to the paper's authors separately, but is not itself resolved or contradicted by this entry's narrower implementation scope).
- Status: **APPROVED (2026-10-07)**, option (a). Author approval given in a Claude Code session on 2026-10-07, choosing "Sound fixed-point sub-case (Recommended)": `shape_of_fold` takes the already-computed `κ0` and one-step `κ1=Kb(·,κ0)`; returns `κ0` (by pointer identity) when structurally equal, else raises `SIZ008`; the broader literal-unrolling and general fixed-point cases are explicitly deferred, disclosed as an open limitation, not hidden.
- Implementation refinement (direct application of `AM-028`'s already-settled precedent, not a fresh ambiguity): this entry's own text above describes a single boolean "do `κ0`/`κ1` coincide" check, but the shipped `shape_of_fold` distinguishes *why* they fail to coincide, mirroring `join_shapes`'s own two-tier handling. A *structural* mismatch (different shape kind, array capacity, or product arity at any level) is `INT001`, not `SIZ008` — since T-Fold/`TYP010` already guarantees the fold body's synthesized type matches the accumulator's own declared type at every iteration, `κ0` and `κ1` provably share the same static type for any real, legitimately-typechecked fold, the identical reasoning `AM-028` already established for `join_shapes`'s own mismatch branches (a structural mismatch is a caller precondition violation, not a program property). `SIZ008` is reserved for the narrower, genuine case: same structure, but an exact/upper term or a nested element/component shape actually differs.

## AM-034 — Scoping the remaining Table 6 rules (`C-ABI`, `C-Len-E`, `C-Len-U`, `C-Call`): `C-ABI`'s own operational role is genuinely unclear from the primary text alone, while `C-Len-E`/`C-Len-U` are independently, narrowly implementable now

- Source location: `main.pdf` Table 6 (p.38): `C-ABI` — "ABI length symbol `n_x`, declaration capacity `N`" → "`(n_x,N;n_x)` and `0≤n_x≤N`"; `C-Len-E` — "`e` has `array(s,u,N;κ̄)`" → "`(s,u;ν)` with `ν=s`"; `C-Len-U` — "`e` has `array(⋆,u,N;κ̄)`" → "`(⋆,u;ν)` with `0≤ν≤u`"; `C-Call` — "earlier summary `Q_f`; simultaneous actual substitution is certified" → "instantiated `(λ,u;ν)`, or `⋆` when an exact actual is absent". `main.pdf` p.11 main text (already load-bearing for `AM-030`): "ABI array argument `x:arr⟨τ,N⟩` receives a fresh formal length `n_x` under `0≤n_x≤N`. Its shape is `array(n_x,n_x,N;capshape(τ))`." `main.pdf` p.12: "`n_x` seeds `Γ_sz` so `K_f(n⃗)` is checked with the body and stored in `Σ`" — i.e. `n_x` is used to seed the SHAPE context when checking a function's own body to build its `K_f`. `AM-003` (already approved): `Σ(f)=(signature, K_f, Q_f?, Φ_f, rank)`, with `Q_f` "derived under exactly the same formal parameters, formal array-length symbols, constraints, and declaration rank as `K_f`" — so `n_x` plausibly seeds an analogous certificate/count context (`Δ`) for `Q_f`'s own construction too, by direct analogy. `src/source/size/shape/.../shape.hpp`'s `shape_of_len` doc comment (fifth slice, already-approved): "this is what will let Table 6's still-deferred `C-Len-E`/`C-Len-U` pull `(λ,u)` from an already-computed Table 8 shape in a later, separately-scoped cross-module slice" — an explicit prior anticipation of exactly this slice's own design.
- Ambiguity, part one (`C-ABI`): unlike every other Table 6 row, `C-ABI`'s own "Premises" column names no source expression `e` at all (contrast `C-Len-E`'s "`e` has..." or `C-Idx`'s "body index `i` under..."). Table 6's own closing sentence (App. A.4, p.37: "No other expression derives a count refinement") implies every row corresponds to deriving a judgment for *some* `e` — but no candidate surface expression cleanly fits `C-ABI`'s own result, `(n_x,N;n_x)` [upper `=N`, the *capacity*]: it is not `len(x)` for an ABI parameter `x`, since `x`'s own Table 8 shape (the already-approved-but-unimplemented ABI-array-parameter rule, `AM-030`) is `array(n_x,n_x,N;capshape(τ))` — an *exact* shape with `λ=u=n_x` — so `len(x)` would route through `C-Len-E` instead, giving `(n_x,n_x;ν=n_x)` [upper `=n_x`, strictly *tighter* than `C-ABI`'s own `N`]. Two genuinely different rules giving two different (both individually sound, differently-tight) upper bounds for what looks like the same quantity is not itself a contradiction (a looser bound is still a valid, if less useful, derivation), but it means `C-ABI` is not simply "the rule for `len` of an ABI parameter" — some other, not-yet-identified source expression or synthetic context-seeding role is its actual trigger. The most textually-supported reading: `C-ABI` is not invoked via any ordinary `infer_count` call site reachable from a body expression at all; it is the rule that seeds the *initial* `Δ`/count-refinement context for a function declaration's own formal ABI array parameters, consumed when constructing `Σ(f)`'s own `K_f`/`Q_f` (paralleling `n_x` seeding `Γ_sz` for `K_f`, p.12, and `AM-003`'s "same formal parameters... as `K_f`" for `Q_f`) — i.e. `C-ABI` belongs to the *not-yet-designed* `Σ`/`K_f`/`Q_f`-construction machinery, the same machinery `C-Call` needs, not to an independent, narrowly-scopable `infer_count` extension the way `C-Idx` was.
- Ambiguity, part two (`C-Len-E`/`C-Len-U`): these two rows are operationally clear in principle (read `(λ,u)` directly off an already-known Table 8 shape for `len(e)`'s own operand `e`), but implementing them raises two real design choices neither already-approved amendment nor any existing doc comment settles: (a) whether `infer_count` should take a new, `src/source/size/shape::ShapeContext`-shaped parameter at all — a first-ever dependency from `src/source/size/count` on `src/source/size/shape` (currently sibling modules with no dependency either direction; `docs/architecture.md`'s own module table does not distinguish between them, both being part of one planned `src/source/size` row, so this is architecturally permitted but not yet precedented); and (b) whether this slice should scope to only the case where `LenExpr::array` (`ast::LenExpr`'s own operand field, an arbitrary `ExprPtr`, not restricted to a bare variable reference) is itself a `VarExpr` with an already-recorded `ShapeContext` entry — mirroring `C-Idx`'s own narrow "via a caller-supplied context, not full live `ast::Expr` traversal" scoping (`AM-026`) — deferring the fully general case (an arbitrary `e`, needing the still-undeferred `infer_shape` dispatcher to compute its own shape first) to a later, separately-scoped slice.
- Recommendation: option (a) **[recommended]** — split the two problems. Do **not** guess at `C-ABI`'s operational trigger now. (2) Implement `C-Len-E`/`C-Len-U` as this session's actual next milestone, independently of (1): `infer_count` gains a new, optional `shape::ShapeContext`-typed parameter (default-empty, so every existing call site is unaffected, mirroring `index_context`'s own default-empty precedent); a new `infer_len` handles `LenExpr` specifically when `array` is a `VarExpr` whose resolved binding has a recorded shape — `C-Len-E` when that shape's own `exact` is present, `C-Len-U` otherwise — raising `SIZ003` (today's existing "no rule" behavior) for any other operand shape, exactly mirroring `C-Idx`'s own narrow, already-approved precedent of deferring full live-traversal support to a later slice.
- Alternative options considered: (b) treat all four remaining rows as one single blocked unit, implementing neither `C-Len-E`/`C-Len-U` nor anything else here until the full `C-ABI`/`C-Call`/`Σ`/`K_f`/`Q_f` design is complete — not recommended, since `C-Len-E`/`C-Len-U` are independently well-understood and narrowly implementable today with no dependency on resolving `C-ABI`'s own open question, and this project's own established practice (e.g. `C-Idx` implemented and `spec-auditor`-reviewed four slices before `check_module_count_admissibility` wired it into live traversal) favors real, soundly-scoped incremental progress over waiting for an unrelated harder problem to resolve first.
