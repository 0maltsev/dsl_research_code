**The soundness bug and its fix**, in detail: the originally-approved `AM-023` reading for `C-Sub` certified `u2<=cert u1` (upper bounds only), reasoning by analogy with `C-Add` (where upper-bounds-only certification is sound, since addition is monotonic increasing in both operands). This reasoning does not transfer to subtraction: `NW_-`'s real content is a *lower* bound on the minuend (`ν2<=ν1`), and `u1` is only ever an *upper* bound on `ν1` — sound only when `u1` happens to be tight (`λ1` present and equal to `u1`). A first `spec-auditor` review of this slice independently constructed the counterexample `(i32bits(10)-i32bits(9))-i32bits(2)`: the inner subtraction produces `(λ=1, u=10)` (Table 6 keeps `C-Sub`'s upper bound at `u1` even when the real value is tighter — paper-specified looseness, not itself a bug), so the outer subtraction's real operands are `ν1=1, ν2=2`, violating `NW_-`'s `ν2<=ν1`; but the old certificate (`u2<=u1`, i.e. `2<=10`) wrongly passed. This session independently reproduced both the pre-fix acceptance (`ok=true`) and, after the fix, the correct rejection (`SIZ006`) against the compiled libraries before escalating.

Fix, via `AM-025` (reopening `AM-023`'s `C-Sub` portion only): certify `u2<=cert λ1` instead, requiring `λ1` present at all (if the minuend is itself inexact, reject via `SIZ006` — there is no sound lower bound on `ν1` available from `(λ,u)` tracking alone in that case). Sound because `λ1`, when present, equals `ν1` exactly (`main.pdf` Sec. 4.2, p.10), so `ν2<=u2<=cert λ1=ν1` chains via transitivity. Strictly more conservative than the buggy reading (rejects a superset of what it wrongly accepted, accepts nothing new) — disclosed cost: a dynamically-safe subtraction nested under an operand with a loose upper bound but a tight exact value available only transitively (e.g. `2-(10-9)`, really `1`, safe) is still statically rejected, a precision loss `AM-025` itself names, not a soundness defect.
